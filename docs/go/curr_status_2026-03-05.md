# Текущий статус проекта: Переход с Python (Django) на Go

**Дата:** 2026-03-05
**Целевая аудитория:** Руководство, Менеджмент

## 1. Краткое резюме (Executive Summary)

Проект по переходу от унаследованного (legacy) монолитного бэкенда PUM, написанного на Python (Django), к новой архитектуре микросервисов на Go, перешел в стадию активной реализации. Основная долгосрочная цель заключается не только в модернизации серверной части для повышения производительности и отказоустойчивости, но и в последующей замене устаревшего графического интерфейса пользователя (GUI) на новый статический интерфейс.

Текущая фаза проекта (Phase 1) сфокусирована на создании прочного фундамента микросервисов, реализации моков (mocking) для внешних зависимостей и обеспечении обратной совместимости со старым интерфейсом, что позволяет поэтапно заменять старую логику без остановки бизнес-процессов.

## 2. Глобальные цели проекта

*   **Архитектурная модернизация:** Переход от жестко связанного монолита Django к распределенной, масштабируемой и независимо развертываемой архитектуре микросервисов на языке Go.
*   **Изоляция и автономность данных:** Замена централизованной базы данных (как в Django) на легковесные локальные хранилища данных (SQLite) для каждого микросервиса.
*   **Гибкость в интеграциях:** Отвязка нового приложения от живой инфраструктуры за счет трехуровневой системы мокирования (внутренние заглушки, эмуляция и реальные подключения) для сторонних систем, таких как Zabbix, GLPI, RabbitMQ и LDAP.
*   **Оптимизация внутренней логики:** Замена медленных внутренних механизмов (например, Redis для Celery-задач) на нативные возможности языка Go (горутины и каналы).
*   **Подготовка к новому интерфейсу:** Формирование API и архитектурного слоя, с которым новый графический интерфейс сможет взаимодействовать напрямую, минуя промежуточный слой обратной совместимости.

## 3. Чего мы достигли на данный момент (Достигнутые результаты)

На сегодняшний день реализованы следующие ключевые компоненты и функционал:

### 3.1. Создание микросервисного ядра
Вся основная логика монолита была разделена и переписана в виде независимых микросервисов на Go (находятся в директории `services/`):
*   **`identity`:** Управление доступом на основе ролей (RBAC) и интеграция с LDAP. Реализована модель логов аудита (`ActivityLog`), дублирующая старый middleware Django.
*   **`gws`:** Создан новый микросервис для управления сетевыми шлюзами и сессиями (локальное хранение `models.Gw` и `models.Session` в SQLite).
*   **`keyservice`:** Реализован микросервис для обработки заявок на передачу ключей.
*   **`inventory`:** Добавлены заглушки (mock endpoints) для списков оборудования (PDU и IPMI), заменяющие старый Django-модуль `data`.
*   **`network`:** Реализованы конечные точки для DHCP и DNS, симулирующие ответы, которые ранее возвращались через RabbitMQ RPC.
*   **`external-data`:** Разрозненные точки мониторинга проблем (узлы и Zabbix) успешно консолидированы в единый endpoint `/problems`.
*   **`task`:** Механизм фонового отслеживания задач, использующий нативные горутины вместо устаревшего стека Redis + Celery.

### 3.2. Слой обратной совместимости (Compatibility Bridge)
Разработан микросервис `services/compatibility`, который выполняет роль моста. Он перехватывает запросы со старыми Django API-адресами от легаси GUI и прозрачно проксирует их к новым Go микросервисам. Это позволяет старому интерфейсу продолжать работу, пока разрабатывается новый интерфейс. В данный момент заглушки из слоя совместимости активно удаляются по мере готовности микросервисов (`gws`, `inventory` и т.д. уже проксируются корректно).

### 3.3. Трехуровневая стратегия эмуляции внешних систем
Внедрена гибкая система управления внешними зависимостями (настраивается глобально через `system.yaml`). Доступны три режима:
1.  **Mock (Заглушки):** Внутренний Go-код генерирует статические ответы.
2.  **Emulated (Эмуляция):** Подключение к локальным серверам-эмуляторам (RabbitMQ, LDAP, Zabbix/GLPI через JSON-RPC/REST).
3.  **Real (Реальные данные):** Прямое подключение к боевым серверам.

Особое внимание уделено аппаратным контроллерам (через RabbitMQ) и LDAP. Зависимости реализованы через паттерн Фабрика (`pkg/external/factory.go`) и покрыты тестами.

### 3.4. Улучшение наблюдаемости интерфейса (UI Observability)
Слой администрирования (`frontend` микросервис) расширен. Теперь панель управления (Admin UI) выводит:
*   Реестр запущенных микросервисов с их реальными внутренними URL для маршрутизации (например, `http://localhost:8091`).
*   Панель состояния внешних зависимостей (LDAP, Zabbix, RabbitMQ) и их текущий режим (mock, emulated, real).

## 4. Ключевые отличия между текущим состоянием и оригинальным репозиторием Django

В процессе перехода были переосмыслены и оптимизированы многие архитектурные решения оригинального монолита:

| Характеристика | Оригинальный репозиторий (Django) | Новая архитектура (Go) |
| :--- | :--- | :--- |
| **Архитектура** | Монолитное приложение (все компоненты тесно связаны). | Набор распределенных микросервисов. |
| **Базы Данных** | Единая реляционная БД для всего приложения (напр. PostgreSQL/MySQL). | Локальные SQLite базы данных для каждого микросервиса (независимое хранение). |
| **Фоновые задачи** | Использование связки Celery + Redis (`TaskRecord`). | Использование нативных горутин (Goroutines) и каналов Go (внешний Redis не обязателен). |
| **Очереди сообщений** | Обязательное использование RabbitMQ как для внутренних, так и для внешних команд. | Внутренняя связь идет через REST/gRPC. RabbitMQ сохранен **только** как строгая граница для связи с физическим оборудованием. |
| **API Эндпоинты** | Избыточность эндпоинтов мониторинга проблем (`nodes-problems` и `zabbix_problems` существовали раздельно). | Эндпоинты оптимизированы: `nodes-problems` и `zabbix_problems` слиты в один `/problems`. |
| **Поддерживаемые сервисы** | Поддерживались заказы на конфигурацию как для `data_services`, так и для `key_services`. | Модуль `data_services` признан устаревшим (Deprecated) и удален. Поддерживается только `key_services`. |
| **Сессии шлюзов** | Наличие излишней истории `/gws/historysession/`. | Функционал `/gws/historysession/` признан ненужным в новой архитектуре и удален. |
| **Связь с GUI** | Шаблонизатор Django возвращал готовые HTML страницы с жесткой привязкой к бэкенду. | Слой совместимости транслирует Django API. В будущем интерфейс будет взаимодействовать с независимыми микросервисами напрямую. |

## 5. Следующие шаги

1.  **Полный отказ от слоя совместимости:** После окончательной реализации и стабилизации всех микросервисов, необходимо будет перевести графический интерфейс на прямое взаимодействие с сервисами Go, минуя микросервис `compatibility`.
2.  **Завершение работы над новым интерфейсом:** Переход к полноценному внедрению нового статического интерфейса в качестве основного инструмента работы с бэкендом.
3.  **Расширение стратегии скрапинга (Scraping):** Продолжение сбора реальных JSON и RabbitMQ структур из боевой старой системы (например, полные карты сетей Zabbix) для автоматической генерации точных Go-структур и моков.
