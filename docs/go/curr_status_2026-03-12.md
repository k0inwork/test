# Текущий статус проекта: Переход с Python (Django) на Go

**Дата:** 2026-03-12
**Целевая аудитория:** Руководство, Менеджмент

---

## 1. Краткое резюме (Executive Summary)

Проект по переходу от унаследованного (legacy) монолитного бэкенда PUM (на базе Django) к современной архитектуре микросервисов на Go продолжает свое активное развитие. С момента последнего отчета (от 5 марта) фокус сместился с создания базового микросервисного ядра на интеграцию продвинутых механизмов оркестрации, наблюдаемости и безопасности, а также на глубокую интеграцию с новым графическим интерфейсом на базе технологии WebAssembly (WASM).

Текущая фаза (Phase 2) активно внедряет замену устаревшему графическому интерфейсу, используя статический GUI, работающий через локальную среду, а также расширяет функционал микросервисов для покрытия последних "слепых зон" оригинального монолита.

## 2. Глобальные цели проекта

*   **Архитектурная модернизация:** Полный переход от монолита к распределенной архитектуре микросервисов на Go с независимыми базами данных SQLite.
*   **Гибкость интеграций и мокирования:** Трехуровневая система (mock, emulated, real) для бесшовной подмены внешних зависимостей (LDAP, Zabbix, RabbitMQ).
*   **Безопасность и наблюдаемость:** Внедрение современных стандартов распределенной трассировки и аудита всех действий пользователей.
*   **Новый графический интерфейс (GUI):** Переход на локальный статический интерфейс с использованием WASM, полностью избавляющий от необходимости серверного рендеринга (Django Templates).
*   **Оркестрация процессов:** Замена устаревшего стека Celery/Redis на нативные механизмы Go для управления фоновыми и регулярными задачами.

## 3. Новые достижения (Что добавлено с 5 марта)

С момента последнего отчета были реализованы следующие крупные обновления и новые функции:

### 3.1. Развитие графического интерфейса (Новый GUI и Apptron)
*   **Интеграция с локальной WASM-средой (Apptron Phase 2):** Реализована поддержка загрузки и запуска локального окружения через бандлы WebAssembly (включая эмуляцию v86, ядра и файловых систем `tarfs`/`httpfs`). Это позволяет запускать терминалы и управлять оборудованием напрямую из браузера, минуя серверные прокси (ранее использовался `django_webssh`).
*   **Разработка статических компонентов:** Добавлены новые статические страницы (например, `dashboard.html`, `signin.html`), которые взаимодействуют с новыми Go микросервисами напрямую через REST API. Реализованы функции создания, редактирования и удаления проектов с динамическим обновлением интерфейса.
*   **Мокирование авторизации в Phase 2:** Внедрен обход Hanko-авторизации для локальной разработки с инъекцией валидного dummy JWT токена, что упрощает тестирование фронтенда.

### 3.2. Наблюдаемость и распределенная трассировка (Telemetry)
*   **Интеграция OpenTelemetry (OTel):** Все микросервисы (и слой HTTP-серверов Gin, и клиенты, и запросы к БД через Gorm) теперь оснащены инструментами распределенной трассировки.
*   **Поддержка Prometheus и Jaeger:** Добавлен сбор метрик и визуализация трассировок с использованием Prometheus и Jaeger. Их бинарные файлы загружаются и запускаются автоматически локально (через единый скрипт `start.sh` без использования Docker, согласно строгим требованиям к изоляции).

### 3.3. Оркестрация задач (Task Management)
*   **Машина состояний и расписания (Cron):** Микросервис `task` получил полноценный механизм управления состояниями (INITIATED, PENDING, FINISHED, FAILED, ERROR, ARCHIVED).
*   **Регулярные задачи (Recurring Tasks):** Реализована архитектура "обратных вебхуков" (reverse-webhook), где центральный сервис `task` выступает в роли планировщика (scheduler) и триггерит внутренние конечные точки других микросервисов.
*   **Управление ресурсозависимыми тревогами (Alarms):** Внедрена система автоматического управления тревогами при сбоях связи с внешними ресурсами. Успешное выполнение задач теперь автоматически закрывает связанные тревоги.

### 3.4. Управление пользователями и аудит безопасности
*   **Журналирование (Audit Logs):** Микросервис `identity` расширен централизованным механизмом логгирования аудита. Добавлен `logging.GinMiddleware`, который асинхронно перехватывает все HTTP-запросы (GET, POST и т.д.) по всей системе и сохраняет их в `ActivityLog` (полноценная замена `ActivityLogMiddleware` из Django).
*   **Управление пользователями:** Расширен функционал управления пользователями. Добавлена возможность корректного удаления пользователей (Remove User) в рамках RBAC модели `identity` сервиса, основанной на группах (роли были полностью удалены из системы).

## 4. Сравнение архитектур (Дополненное)

В дополнение к структурным изменениям (разделение на микросервисы, отказ от Redis в пользу Goroutines), добавились новые принципиальные отличия:

| Характеристика | Оригинальный репозиторий (Django) | Текущая архитектура (Go Phase 2) |
| :--- | :--- | :--- |
| **Аудит и безопасность** | Синхронный `ActivityLogMiddleware` в монолите. | Асинхронный централизованный аудит (через `audit` endpoint в `identity` сервисе) с поддержкой распределенной трассировки OTel. |
| **Планировщик задач** | Использование Celery beat + Redis. | Встроенный Cron-планировщик в микросервисе `task` с архитектурой "обратных вебхуков" для вызова других сервисов. |
| **Мониторинг** | Индивидуальные логи, отсутствие сквозного трейсинга. | Централизованные метрики Prometheus и распределенные трассировки Jaeger, автоматический запуск без Docker. |
| **Графический интерфейс** | Серверный рендеринг (Django Templates). | Полностью статический локальный интерфейс на базе WebAssembly (Apptron), взаимодействующий напрямую с API микросервисов. |
| **Управление ролями** | Система "ролей" и прав на базе пользователей. | Строгий контроль доступа исключительно через "группы" (Groups, например `tsumadm`, `devadm`), концепция индивидуальных ролей удалена. |

## 5. Следующие шаги

1.  **Отказ от слоя совместимости (Compatibility Layer):** Перевод оставшихся компонентов статического графического интерфейса на прямое взаимодействие с API микросервисов Go. Слой `compatibility` должен быть постепенно выведен из эксплуатации.
2.  **Завершение Phase 2 (Apptron Worker):** Полная отладка взаимодействия WASM модулей (включая IPC через Unix-сокеты) с нативным Go Host Runner для обеспечения сложного сетевого взаимодействия без ограничений стандартного WASM.
3.  **CI/CD и E2E Тестирование:** Расширение покрытия GitHub Actions (`phase2.yml`) с использованием Playwright скриптов для сквозного тестирования нового статического графического интерфейса в среде Cloudflare Worker.
