# Обзор архитектуры системы

Этот документ предоставляет высокоуровневый обзор архитектуры системы, ее компонентов и их взаимодействия.

## 1. Основные компоненты

Система представляет собой распределенную платформу управления, предназначенную для контроля сетевых устройств, шлюзов и виртуальных машин. Она состоит из следующих основных компонентов:

### 1.1. Бэкенд PUM (Product Unit Management)
- **Фреймворк:** Django 4.0.1
- **Роль:** Центральный узел управления, предоставляет веб-интерфейс и REST/GraphQL API.
- **Обязанности:**
  - Аутентификация и авторизация пользователей (через LDAP/Kerberos).
  - Высокоуровневая бизнес-логика управления продуктами (PDU) и шлюзами.
  - Управление состоянием для конфигураций Multi-Master.
  - Координация фоновых задач.

### 1.2. Брокер сообщений (RabbitMQ)
- **Роль:** Коммуникационная основа для межмодульной координации и взаимодействия между экземплярами ARM.
- **Основные обменники (Exchanges):**
  - `amqp.fanout`: Используется для широковещательной рассылки изменений состояния и команд на несколько экземпляров ARM.
  - Очереди, специфичные для модулей: Используются для связи со специализированными контроллерами (например, `netdevcheker`, `switch-ctrld`).

### 1.3. Очередь задач и бэкенд результатов (Redis)
- **Брокер для Celery:** Обрабатывает распределение асинхронных задач.
- **Слой Django Channels:** Управляет WebSocket-соединениями для обновления интерфейса в реальном времени.
- **Хранилище общего состояния:** Кастомные абстракции (`RedisStore`, `RedisVar`) хранят переменное состояние, разделяемое между различными процессами Python.

### 1.4. Сетевые шлюзы (bpkgw)
- **Фреймворк:** Flask
- **Роль:** Низкоуровневое управление сетевыми интерфейсами.
- **Обязанности:**
  - Создание и удаление туннелей VXLAN с помощью команд `ip link`.
  - Мониторинг трафика (TX байты) на интерфейсах туннелей.
  - Предоставление REST API для управления сессиями.

## 2. Потоки взаимодействия

### 2.1. Внутренние (Django — Воркеры)
Приложение Django отправляет задачи воркерам Celery через Redis. Эти воркеры обрабатывают длительные операции, такие как синхронизация с внешними системами или сложные сетевые конфигурации.

### 2.2. Межмодульные (RabbitMQ)
Для связи с внешними контроллерами оборудования или другими экземплярами ARM система использует RabbitMQ. Кастомный `PikaChannelSingleton` обеспечивает эффективное управление соединениями, а библиотека `event_consumer` позволяет воркерам Celery реагировать на входящие сообщения RabbitMQ.

### 2.3. Координация Multi-Master
Система поддерживает несколько экземпляров «Master». Они координируют свое состояние (кто в данный момент является активным мастером), транслируя сообщения через обменник `amqp.fanout` в RabbitMQ. Redis используется для отслеживания обработанных запросов.

## 3. Внешние интеграции
- **LDAP/Kerberos:** Централизованная аутентификация.
- **GLPI:** Используется в качестве CMDB для синхронизации информации о продуктах/дата-центрах.
- **Zabbix:** Мониторинг устройств и состояния сети.
- **QEMU:** Управление виртуализацией, обычно используется для шлюзов или сред тестирования.
- **Graylog:** Централизованное логирование системных событий.

# Обзор компонентов приложения

Этот документ содержит краткий обзор различных приложений и модулей в системе PUM, подчеркивая их основные обязанности и технические роли.

## 1. Основная платформа управления (приложения Django)

### 1.1. `products`
Управляет жизненным циклом **устройств распределения питания (PDU)** и операционных единиц. Обрабатывает интеграцию с GLPI для синхронизации инвентаризации и географического отображения (ГИС) физических активов.

### 1.2. `gws` (Шлюзы)
Организует высокоуровневое управление **сетевыми шлюзами** и создание виртуальных сессий (туннелей VXLAN) между ними. Связывает пользователей с конкретными сетевыми топологиями.

### 1.3. `data` (Сетевое оборудование)
Фокусируется на низкоуровневой инвентаризации **коммутаторов и портов**. Отслеживает физические соединения (`SwitchConnection`) и клиентские назначения (`SwitchCustomerConnection`), а также инициирует автоматические обновления конфигурации через специализированные модули.

### 1.4. `services` (Сервисы связи)
Предоставляет высокоуровневые абстракции для сервисов передачи данных и ключей. Управляет «заказами» на подключение (`KeyService`, `DataService`), координируя необходимые конфигурации коммутаторов и шлюзов для удовлетворения требований клиентов.

### 1.5. `tasks` (Отслеживание операций)
Центральный узел для отслеживания асинхронных операций. Ведет постоянный учет системных задач (`TaskRecord`), статуса их выполнения и результатов, предоставляя данные для индикаторов прогресса в интерфейсе и журналов аудита.

### 1.6. `accounts` (Идентификация и безопасность)
Управляет пользователями, пользовательскими ролями и детализированными разрешениями. Интегрируется с LDAP/Kerberos и реализует систему `ActivityLog` для аудита безопасности.

### 1.7. `core` (Основа системы)
Содержит общую библиотеку утилит, базовые модели (`GlobalSettings`), механизмы распределенной блокировки и кастомные уровни связи RabbitMQ/Redis, используемые всеми остальными приложениями.

### 1.8. `network`
Управляет распределением IP-адресов и взаимодействием с контроллерами DNS/DHCP. Обрабатывает логику предоставления логических сетей поверх физического оборудования.

## 2. Специализированные контроллеры и модули

### 2.1. `bpkgw` (Контроллер VXLAN)
Сервис на базе Flask, который выполняет низкоуровневые сетевые команды Linux для создания, удаления и мониторинга **туннелей VXLAN**. Обеспечивает фактическое управление «плоскостью данных» (data plane).

### 2.2. `control` (Менеджер состояния)
Легковесный контроллер, который управляет операционным состоянием (START/STOP/REBOOT) и сбором логов для управляемых сущностей через HTTP или RabbitMQ RPC.

### 2.3. `modules/` (Прокси оборудования)
Набор модулей Python (IPMI, PDU, Switch и т. д.), которые действуют как асинхронные прокси для специализированного оборудования. Они транслируют высокоуровневые вызовы Python в специфические сообщения протокола (RabbitMQ) для выделенных контроллеров.

### 2.4. `django_webssh`
Предоставляет интегрированный терминал для безопасного удаленного доступа к управляемому оборудованию, включая запись сессий для соблюдения аудита.

## 3. Инфраструктурные сервисы

- **`ftpserver`**: Специализированный FTP-сервис для управляемых устройств для загрузки/выгрузки резервных копий конфигураций и логов.
- **`rabbitmq` и `redis`**: Коммуникационная основа для передачи сообщений, очередей задач и кэширования распределенного состояния.
- **`ldap` и `kerberos`**: Внешние поставщики удостоверений для централизованной аутентификации.
- **`bind` и `isc`**: Базовые сервисы для управления DNS и DHCP, управляемые через `ip-module`.

# Анализ моделей данных

Этот документ объясняет основные структуры данных и модели Django, используемые в системе.

## 1. Управление продуктами (PDU)
Приложение `products` управляет основными сущностями, которыми контролирует система.

### 1.1. Модель продукта (`products.models.Product`)
Представляет физическое или виртуальное устройство (PDU, OU).
- **Основные поля:**
  - `name`, `pouType`, `sequential_number`, `region`: Идентифицируют устройство.
  - `state`: Текущий операционный статус.
  - `geo`, `long`, `lat`: Географическое положение для отображения на карте.
  - `glpi_uuid`: Ссылка на CMDB GLPI.
- **Логика синхронизации:** Включает методы для двусторонней синхронизации с GLPI, обрабатывая сложные соглашения об именовании (например, `REGION/#seq-POU name`).

### 1.2. Модель запросов (`products.models.Requests`)
Отслеживает асинхронные запросы, отправленные на устройства или другие модули.
- **Поля:** `request`, `response`, `pending`, `error`, `request_timeout`.
- **Цель:** Обеспечивает журнал аудита и отслеживание состояния для операций, выполнение которых может занять время.

## 2. Управление шлюзами и сессиями
Приложение `gws` занимается оркестрацией сетевых туннелей.

### 2.1. Модель шлюза (`gws.models.Gw`)
Представляет сетевой шлюз.
- **Поля:** `address`, `region`, `state`.
- **Логика:** Подключается к физическим или виртуальным шлюзам (часто под управлением сервиса `bpkgw`).

### 2.2. Модель сессии (`gws.models.Session`)
Представляет туннель VXLAN между двумя шлюзами.
- **Поля:**
  - `gw1`, `gw2`: Две конечные точки туннеля.
  - `subnet`: Сетевой адрес, назначенный туннелю.
  - `tx_bytes`: Статистика трафика, собранная со шлюза.
- **Использование:** Сессии создаются динамически через REST API `bpkgw` для установления безопасных туннелей между регионами.

## 3. Глобальная конфигурация (`core.models.GlobalSettings`)
Хранилище «ключ-значение» в базе данных для общесистемных настроек.
- **Использование:** Хранит такие настройки, как текущий Master ARM, конфигурация LDAP, префиксы Zabbix и т. д.
- **История:** Использует `django-simple-history` для отслеживания изменений критических настроек.

## 4. Отслеживание задач (`tasks.models.TaskRecord`)
В то время как Celery занимается выполнением, `TaskRecord` обеспечивает постоянную запись в базе данных о том, какие задачи были запущены, кем и каковы их результаты. Это важно для аудита и обеспечения обратной связи в интерфейсе.

# Анализ Celery и RabbitMQ

Этот документ содержит глубокое погружение в то, как система использует Celery и RabbitMQ, уделяя особое внимание управлению соединениями и паттерну «специальный воркер».

## 1. Управление соединениями RabbitMQ

Чтобы избежать исчерпания соединений и каналов, система использует кастомный паттерн синглтон для `pika`.

### 1.1. PikaChannelSingleton (`core.pika.py`)
- **Паттерн:** Синглтон-обертка вокруг `pika.BlockingConnection`.
- **Цель:**
  - Гарантирует, что на каждый процесс открывается только одно соединение для каждого типа подключения.
  - Автоматически обрабатывает переподключение, если соединение разрывается или закрывается.
  - Используется совместно задачами Celery и приложением Django.
- **Эффективность:** Это критически важно для стабильности системы, особенно когда множеству кратковременных задач необходимо взаимодействовать с RabbitMQ.

## 2. Паттерн «Специальный воркер»

Система использует два типа воркеров Celery:

### 2.1. Стандартный воркер Celery
- **Брокер:** Redis.
- **Использование:** Стандартные асинхронные задачи (например, обслуживание базы данных, периодические синхронизации).
- **Конфигурация:** Определяется в `products_app/settings.py` через `CELERY_BROKER_URL`.

### 2.2. Воркер, привязанный к RabbitMQ (Специальный воркер)
- **Библиотека:** `event_consumer`
- **Механизм:** Этот воркер использует `AMQPRetryConsumerStep` в Celery.
- **Функциональность:** Он прослушивает определенные очереди RabbitMQ и сопоставляет входящие сообщения с функциями Python, декорированными `@message_handler`.
- **Пример использования:** Меж-ARM взаимодействие (Multi-Master) и интеграция с внешними модулями, такими как `ASU-X`.

## 3. Паттерны взаимодействия RabbitMQ

### 3.1. RPC (Remote Procedure Call — Удаленный вызов процедур)
Реализовано в `products/tasks.py` через `RpcClient` и `RpcClientAsync`.
- **Рабочий процесс:**
  1. Создает эксклюзивную, недолговечную очередь обратного вызова (callback queue).
  2. Публикует сообщение с `correlation_id` и установленным `reply_to` на очередь обратного вызова.
  3. Ожидает (блокирующим или асинхронным способом) ответа в очереди обратного вызова.

### 3.2. Fanout (Широковещательная рассылка)
Реализовано через `FanoutClient`.
- **Использование:** Используется для трансляции изменений состояния на все ARM (например, команда `change_master`).
- **Обменник (Exchange):** `amqp.fanout`.

## 4. Настройка производительности
- **`CELERY_WORKER_PREFETCH_MULTIPLIER=0`**: Предварительная выборка отключена для обеспечения справедливого распределения задач между воркерами, что важно для длительных или сетевых задач с интенсивным вводом-выводом.
- **`CELERY_BROKER_POOL_LIMIT=100`**: Позволяет увеличить количество одновременных соединений с брокером Redis.
- **`celery_pool_asyncio`**: Система настроена на использование пула, совместимого с asyncio, для Celery, что позволяет определять задачи как `async def` и использовать `await`.

# Анализ использования Redis

Redis является многоцелевым компонентом системы, выступая в роли брокера сообщений, кэша и хранилища общего состояния.

## 1. Кастомные абстракции хранилища (`core.redisbackend.py`)

Система не использует Redis как простое хранилище «ключ-значение». Она реализует несколько абстракций для структурированного хранения данных:

### 1.1. RedisStore
- **Роль:** «Объектно-реляционное» отображение для Redis.
- **Механизм:** Хранит объекты в виде строк JSON. Поддерживает набор идентификаторов (`index:<ClassName>:id`) и индексацию определенных полей с использованием Redis Hashes (`index:<ClassName>:<FieldName>`).
- **Пример использования:** Хранение эфемерных объектов, таких как `TaskRecord`, которым требуется быстрый доступ и истечение срока действия, но не нужны накладные расходы SQL-базы данных.

### 1.2. RedisVar
- **Роль:** Типизированное хранилище переменных.
- **Механизм:** Обрабатывает сериализацию/десериализацию типов Python (включая `set`) в JSON.
- **Особенность:** Включает менеджер контекста `lock()` для распределенной блокировки, обеспечивая атомарные обновления общих переменных.

### 1.3. RedisHashTable
- **Роль:** Обертка для Redis Hashes (`HSET`, `HGET`).
- **Механизм:** Предоставляет интерфейс, подобный словарю, для Redis Hashes с автоматическим отслеживанием времени доступа и модификации.

## 2. Инфраструктурные роли

### 2.1. Брокер Celery
Все стандартные задачи Celery ставятся в очередь в Redis. Это отделено от специализированного взаимодействия через RabbitMQ.

### 2.2. Django Channels
Redis служит вспомогательным хранилищем для `CHANNEL_LAYERS`, обеспечивая связь в реальном времени (WebSockets) между бэкендом и браузером.

### 2.3. Состояние и координация задач
- **`REDIS_PERIODIC_CACHE`**: Хранит список и время выполнения периодических задач, чтобы гарантировать их запуск с правильными интервалами во всем кластере.
- **`REDIS_PROCESSED_REQUEST`**: Отслеживает обработанные запросы Multi-Master для предотвращения дублирования обработки.
- **`REDIS_ARM_ID`**: Хранит уникальный идентификатор для текущего экземпляра ARM, гарантируя, что он может идентифицировать свои собственные сообщения в широковещательных обменах.

## 3. Пулинг соединений
`RedisConnection` реализует синглтон `ConnectionPool`. Это гарантирует, что приложение не создает новое TCP-соединение для каждой операции Redis, что значительно повышает производительность и снижает потребление ресурсов.

# Система взаимодействия модулей

Система использует архитектуру на основе реестра для управления взаимодействием с внешними сервисами и контроллерами оборудования. Этот паттерн обеспечивает высокую степень развязки (decoupling) между бизнес-логикой Django и базовыми протоколами связи.

## 1. Паттерн Service Locator (`Module.getModule`)

Ядром системы является базовый класс `Module` в `modules/base.py`, который выступает в роли реестра всех доступных сервисных модулей.

### 1.1. Регистрация
Модули регистрируют себя во время инициализации:
```python
Module.registerModule(LazyProxy(lambda: PDUModule(queue)), "pdu-module")
```
Использование `LazyProxy` гарантирует, что модуль (и его потенциально тяжелая логика инициализации или соединения) будет создан только при первом обращении.

### 1.2. Получение
Любая часть приложения может получить ссылку на модуль, не зная его конкретной реализации:
```python
module = Module.getModule("pdu-module")
await module.statusRelayAll(ip="192.168.1.100")
```

## 2. Динамическое отображение команд

Многие модули (например, `PDUModule`, `IPMIModule`, `SwitchConfigModule`) используют магический метод Python `__getattr__` для динамического сопоставления вызовов методов с командами RabbitMQ.

- **Рабочий процесс:**
  1. Вызывается метод, например `statusRelayAll()`, у экземпляра модуля.
  2. Поскольку метод не определен явно, его перехватывает `__getattr__`.
  3. Формируется полезная нагрузка: `{'command': 'statusRelayAll', 'params': {...}}`.
  4. Полезная нагрузка отправляется через RabbitMQ, и ожидается ответ.

Такая конструкция позволяет коду Python поддерживать новые команды от контроллеров оборудования без необходимости внесения изменений в определения модулей.

## 3. Распределенная ретрансляция запросов

Система поддерживает гибридную модель выполнения, чтобы длительные операции RabbitMQ не блокировали асинхронный цикл веб-приложения.

### 3.1. Локальное выполнение против выполнения воркером
Метод `RabbitMqModule.call` проверяет флаг `settings.CURRENT_WORKER`:
- **Если `True` (внутри воркера):** Модуль выполняет вызов RabbitMQ напрямую с помощью `pika`.
- **Если `False` (внутри веб-приложения):** Запрос ретранслируется фоновому воркеру через Django Channels.

### 3.2. Асинхронное хранение результатов
При ретрансляции запроса:
1. Веб-приложение генерирует `corr_id` и отправляет запрос в канал `send-rpc`.
2. `FanoutConsumer` (специальный воркер) получает запрос и выполняет фактический вызов RabbitMQ.
3. Воркер сохраняет ответ в Redis Hash (`variables.RABBITMQ_ASYNC_RESULT_TABLE`) под ключом `corr_id`.
4. Веб-приложение опрашивает или ожидает результат в Redis.

## 4. Основные зарегистрированные модули

| Псевдоним | Реализация | Обязанности |
|-------|----------------|----------------|
| `pdu-module` | `PDUModule` | Управление устройствами распределения питания (реле, состояние). |
| `ipmi-module` | `IPMIModule` | Внеполосное управление серверами (питание, сброс). |
| `switch-module` | `SwitchConfigModule` | Конфигурация сетевых коммутаторов и мониторинг состояния. |
| `ip-module` | `DNSDHCPModule` | Управление IP-адресами и конфигурация. |
| `asux-module` | `ASUXModule` | Интеграция с внешней системой ASU-X. |
| `route-module` | `RouteModule` | Управление сетевыми путями и маршрутизацией сессий. |
| `ready-module` | `ReadyModule` | Мониторинг фактора здоровья и готовности. |

## 5. Безопасность и контроль доступа
Большинство модулей наследуются от `AccessControlledMixin`, что позволяет им использовать метод `call_ac`. Это гарантирует, что аппаратные команды проверяются на соответствие разрешениям пользователя и текущему состоянию ресурса перед отправкой в сеть.

  - `load(command)`: Получает текущую конфигурацию или состояние.
  - `send(data)`: Отправляет новые сетевые конфигурации.
- **Формат данных:** Обменивается данными преимущественно в формате **YAML**, обернутом в сообщения RabbitMQ.

- **Реализация:** `SwitchConfigModule` в `modules/equipment.py`.
- **Предполагаемое назначение:** Глубокая конфигурация и мониторинг состояния сетевых коммутаторов.
- **Поверхность API:** `status`, `get_from_device`, `add_new_switch`, `add_new_config`, `set`, `check`.
- **Динамическое отображение:** Использует `__getattr__` для сопоставления вызовов методов Python с командами RabbitMQ, разделенными пробелами (например, `add_new_switch` становится `"add new switch"`).
- **Контекст взаимодействия:** Используется для автоматизированного предоставления коммутаторов и проверки согласованности конфигурации во всей сетевой фабрике.

- **Реализация:** `RouteModule` в `modules/route.py`.
- **Предполагаемое назначение:** Организует сессии L2/L3 и выбор пути через фабрику шлюзов.
- **Поверхность API:**
  - `create(port, bandwidth, priority, uid, session)`: Устанавливает новое соединение.
  - `remove(port, id, session)`: Разрывает существующее соединение.
- **Контекст взаимодействия:** Интенсивно используется `services/tasks.py` во время установления и разрыва сессий. Возвращает ответы JSON, содержащие установленные IP-адреса и идентификаторы соединений.

## 2. Управление оборудованием

### 2.1. `pdu-module` (Контроллер устройств распределения питания)
- **Реализация:** `PDUModule` в `modules/equipment.py`.
- **Предполагаемое назначение:** Управляет физическим электропитанием стоек и отдельных устройств.

### 2.2. `ipmi-module` (Контроллер внеполосного управления серверами)
- **Реализация:** `IPMIModule` в `modules/equipment.py`.
- **Предполагаемое назначение:** Удаленное управление серверами (взаимодействие с BMC — Baseboard Management Controller).
- **Поверхность API:** `status`, `power_on`, `soft_power_off`, `hard_reset`, `ipmi_cold_reset`.
- **Контекст взаимодействия:** Обеспечивает управление «последней надежды» для не отвечающих серверов, позволяя системе выполнять жесткую перезагрузку или контролировать состояние оборудования независимо от ОС.

# Критические системные рабочие процессы

В этом документе пошагово разбирается логика основных системных процессов.

## 1. Координация Multi-Master (отказоустойчивость)

Система гарантирует, что только один ARM является «Master» (основным) для данного региона, в то время как остальные находятся в режиме «Passive» (пассивный).

1. **Триггер:** Запуск ARM или выполнение периодической задачи `check_arm_master`.
2. **Обнаружение:** ARM проверяет свой статус в `GlobalSettings`. Если статус неизвестен, он транслирует команду `get_master` через обменник `amqp.fanout`.
3. **Ответ:** Текущий Master получает запрос `get_master` и транслирует свою идентификацию и причину, по которой он является Master.
4. **Переход:** Если требуется переход (например, через ручную команду), транслируется сообщение `change_master`.
5. **Подтверждение:** Получающие ARM обновляют свои локальные `GlobalSettings` на «PASSIVE» (режим «только чтение»), информируют подключенных клиентов веб-интерфейса через WebSockets и отправляют `change_master_ack`.
6. **Сохранение:** Master ARM отслеживает подтверждения в Redis (`REDIS_PROCESSED_REQUEST`), чтобы убедиться, что переход завершен.

## 2. Создание сессии шлюза (VXLAN)

1. **Триггер:** Пользователь запрашивает соединение между двумя шлюзами в интерфейсе.
2. **Создание модели:** Объект `Session` создается в базе данных Django.
3. **Вызов API:** Бэкенд Django отправляет POST-запрос к REST API `bpkgw` на целевых шлюзах.
4. **Низкоуровневая настройка:** Сервис `bpkgw` (Flask) выполняет `ip link add vxlan...` для создания туннеля.
5. **Обновление состояния:** В случае успеха статус `Session` обновляется, и начинается мониторинг трафика.

## 3. Синхронизация продуктов (GLPI)

1. **Периодический триггер:** `reload_periodic_sync` запускается каждые несколько минут.
2. **Получение данных:** Задача вызывает `glpi_get_datacenters_2`, которая запрашивает API GLPI.
3. **Отображение (Mapping):** Система сопоставляет сущности GLPI с моделью `Product`, используя метод `sync()`.
4. **Разрешение конфликтов:** `sync_search()` используется для поиска существующих записей путем сопоставления сложных паттернов именования.
5. **Обновление:** Создаются новые продукты, а существующие обновляются с текущим статусом и географическим положением.

## 4. Внешняя маршрутизация ASU-X

1. **Прибытие сообщения:** Внешняя система (`ASU-X`) отправляет сообщение в очередь RabbitMQ `asuiks_channels`.
2. **Специальный воркер:** Специальный воркер Celery получает сообщение и запускает `asu_iks_routing`.
3. **Обработка:**
   - Система проверяет коммутаторы и порты конечных точек.
   - Создает запись `KeyService`.
   - Запускает фоновый поток (`wait_for_it`) для мониторинга статуса задачи маршрутизации.
4. **Ответ:** Как только задача маршрутизации завершается (отслеживается через `TaskRecord`), система сообщает результат обратно в `ASU-X` через очередь `reply-to` в RabbitMQ.

# Руководство по внешним интеграциям

Система полагается на несколько внешних сервисов для идентификации, мониторинга и управления инфраструктурой.

## 1. Аутентификация (LDAP и Kerberos)

### 1.1. LDAP
- **Реализация:** Использует `django-auth-ldap`.
- **Конфигурация:** В `settings.py` настроены два бэкенда LDAP (`LDAPBackend1`, `LDAPBackend2`) для избыточности.
- **Отображение групп:** Группы LDAP (например, `tsumadm`, `trafadm`) сопоставляются с разрешениями Django. Это позволяет осуществлять детальный контроль доступа на основе организационных ролей.
- **Поиск:** Настроен поиск пользователей в `ou=users,dc=strela` и групп в `ou=groups,dc=strela`.

### 1.2. Kerberos
- **Использование:** Упоминается в `variables.py` (`KERBEROS_USER`). Обычно используется для сквозной аутентификации (SSO) или безопасного взаимодействия между сервисами.

## 2. Мониторинг (Zabbix)

- **Интеграция:** Система взаимодействует с Zabbix для мониторинга состояния управляемых устройств.
- **Соглашение об именовании:** Продукты (PDU) генерируют свои имена в Zabbix, используя префикс, определенный в `GlobalSettings`.
- **Оповещение:** Система может отображать карты Zabbix на своем дашборде и реагировать на уровни серьезности проблем.

## 3. Управление инвентаризацией (GLPI)

- **Роль:** Источник истины для физической инфраструктуры.
- **Интеграция:** Синхронизируется через кастомную библиотеку (упомянутую в `requirements.txt`) и периодические задачи Celery.
- **Данные:** Синхронизирует названия дата-центров, положения в стойках и статус устройств.

## 4. Виртуализация (QEMU)

- **Использование:** Используется для размещения виртуальных шлюзов или сред тестирования.
- **Управление сетью:** Кастомные скрипты (`qemu-ifup-brcontrol`) управляют мостовыми интерфейсами для виртуальных машин QEMU, позволяя им участвовать в сети VXLAN, управляемой ARM.

## 5. Логирование (Graylog)

- **Роль:** Централизованный сбор логов.
- **Реализация:** Django настроен на отправку логов в Rotating File Handler, которые обычно подхватываются сборщиком логов и пересылаются в Graylog (как настроено в `GlobalSettings`).

# Терминальная система WebSSH

Система PUM включает полнофункциональный веб-терминал SSH, позволяющий администраторам управлять удаленными устройствами непосредственно из браузера.

## 1. Архитектура

Система WebSSH построена с использованием:
- **`django-webssh`**: Приложение Django, предоставляющее пользовательский интерфейс терминала и представления.
- **`asyncssh`**: Библиотека Python для асинхронного SSHv2.
- **Django Channels**: Управляет постоянным соединением WebSocket между браузером и бэкендом.

## 2. Ключевые особенности

### 2.1. Бесшовная аутентификация
Система использует текущую сессию пользователя для аутентификации SSH-соединения. Пароль пользователя (кэшированный в `request.session['stored_password']` при входе) используется автоматически, обеспечивая единый вход (SSO) для удаленного управления.

### 2.2. Запись сессий
При запуске сессии система может записывать все взаимодействие:
- **Сохранение:** Необработанный вывод терминала и данные о времени сохраняются в `/var/log/arm/<uuid>.rec`.
- **Оптимизация:** Записываются только изменения (diffs) экрана терминала, когда это возможно, для экономии места.
- **Фоновая задача:** Периодическая фоновая задача (`call_periodic`) сбрасывает данные на диск каждые 3 секунды, чтобы гарантировать отсутствие потери данных даже при прерывании сессии.

### 2.3. Воспроизведение сессий (Replay)
Система поддерживает воспроизведение записанных сессий:
- **Механизм:** Потребитель `WebSSH` читает файл `.rec` и «воспроизводит» события обратно в браузер, используя исходные данные о времени.
- **Интерактивное воспроизведение:** Пользователи могут приостанавливать воспроизведение с помощью событий мыши (Статус 3).

## 3. Интеграция с аудитом
Каждая SSH-сессия автоматически регистрируется в `ActivityLog`:
- **Регистрируемые данные:** Имя пользователя, целевой хост, исходный IP и имя файла записи сессии.
- **Соблюдение требований:** Это обеспечивает полный журнал аудита всех команд, выполненных администраторами на удаленном оборудовании.

# Расширенные утилиты и мониторинг

Модуль `core/utils.py` содержит несколько сложных декораторов и движков, которые обеспечивают надежность системы PUM и возможности мониторинга.

## 1. Надежные декораторы

### 1.1. `@timeout(max_time)`
Универсальный декоратор, поддерживающий как синхронные, так и асинхронные функции.
- **Синхронные функции:** Использует отдельный поток и `queue.Queue` для запуска функции и присоединяется к потоку с указанным таймаутом.
- **Асинхронные функции:** Использует `asyncio.wait_for` для нативной обработки таймаута.

### 1.2. `@thread_safe`
Гарантирует, что функция не будет выполняться одновременно несколькими процессами или потоками. Использует механизм `redis.lock`, описанный в анализе Redis. Это важно для предотвращения состояний гонки во время конфигурации оборудования.

### 1.3. `@retry(retries=3)`
Простая обертка для автоматического повтора неудачных функций, обычно используемая для сетевых операций, в которых могут возникать кратковременные сбои.

## 2. Система алармов (`@alarm`)

Декоратор `@alarm` — это основной способ, с помощью которого система контролирует состояние своих интеграций.

- **Механизм:**
  1. Если декорированная функция вызывает исключение или превышает время ожидания, декоратор перехватывает это.
  2. Он инициирует сигнал Django `alarm_raised`.
  3. Приемник сигнала в `products_app/signals.py` обновляет `GlobalSettings` (`SETTINGS_ALARMS`).
  4. Состояние всей системы (`SETTINGS_STATE`) меняется на **«ALARM»**.
  5. Уведомление в реальном времени отправляется всем подключенным веб-клиентам через Django Channels.
- **Автоматическое восстановление:** Когда последующий вызов декорированной функции завершается успешно, инициируется сигнал `alarm_shutdown`, который сбрасывает аларм и восстанавливает состояние системы до «ACTIVE» или «PASSIVE».

## 3. Движок рекурсивной сериализации (`jsonify`)

Функция `jsonify` — это кастомный, высокорекурсивный движок сериализации, используемый во всем проекте для преобразования сложных объектов Python и Django в форматы, пригодные для JSON.

- **Особенности:**
  - **Поддержка моделей Django:** Автоматически сериализует модели Django, обрабатывая внешние ключи и отношения «многие ко многим».
  - **Контроль уровня вложенности:** Предотвращает бесконечную рекурсию, позволяя параметру `level` ограничивать глубину сериализации.
  - **Сериализация методов (`@json_attr`):** Разработчики могут помечать методы модели декоратором `@json_attr(level=X)`, чтобы включить результат этого метода в сериализованный вывод.
  - **Поддержка типов:** Встроенная обработка UUID, Enum, объектов datetime (преобразуемых в метки времени) и объектов `LazyProxy`.

# Безопасность и аудит

Система PUM предназначена для сред с повышенными требованиями к безопасности, включая несколько уровней отслеживания активности и контроля доступа.

## 1. Логирование активности

Отслеживание активности реализовано через несколько механизмов:

### 1.1. Отслеживание через Middleware
`ActivityLogMiddleware` (из `django-user-activity-log2`) автоматически записывает все POST и GET запросы в базу данных, фиксируя:
- **Субъект:** Пользователь, совершивший действие.
- **Действие:** URL и HTTP-метод.
- **Контекст:** Исходный IP-адрес и временная метка.

### 1.2. Ручной аудит SSH
Как описано в анализе WebSSH, каждая сессия терминала связана с записью в `ActivityLog`, которая указывает на постоянную запись взаимодействия в терминале.

## 2. Аутентификация и SSO

Система полагается на внешних поставщиков удостоверений для надежной аутентификации:
- **Двойные бэкенды LDAP:** Обеспечивают избыточность для интеграции с корпоративными каталогами.
- **Поддержка Kerberos:** Обеспечивает безопасное взаимодействие между сервисами и потенциальный SSO.
- **CAS (Central Authentication Service):** Интегрирован через `django_mama_cas` для работы в качестве поставщика удостоверений или сервиса.

## 3. Контроль доступа и защита от перебора паролей

### 3.1. `django-axes`
Система использует `axes` для мониторинга попыток входа и блокировки пользователей или IP-адресов после нескольких неудачных попыток (`AXES_FAILURE_LIMIT = 5`). Для обеспечения кастомного взаимодействия с пользователем во время блокировки используется специальное представление (`accounts.views.axes`).

### 3.2. Контроль доступа к оборудованию
`AccessControlledMixin` (используемый сервисными модулями) гарантирует, что аппаратные команды (такие как перезагрузка PDU или сброс сервера через IPMI) ограничиваются детальными разрешениями. Эти команды часто записываются в `ActivityLog`, чтобы критические изменения оборудования всегда можно было отнести к конкретному пользователю.

# Middleware Multi-Master и принудительный режим «только чтение»

Для поддержания согласованности данных в распределенной среде ARM система реализует строгий механизм принудительного режима «только чтение» на экземплярах «Slave» (пассивных).

## 1. Middleware `FilterPOSTOnSlave`

Middleware `FilterPOSTOnSlave` (в `products_app/middleware/middleware.py`) является привратником для всех операций по изменению данных.

- **Работа:**
  1. Оно определяет идентификатор текущего экземпляра (`SETTINGS_TSUM`) и активного мастера кластера (`SETTINGS_CONTROL`) из `GlobalSettings`.
  2. Для каждого входящего `POST` запроса оно проверяет, является ли текущий экземпляр мастером.
  3. **Если пассивный:** Оно вызывает исключение `PermissionDenied` для большинства POST-запросов, фактически переводя все веб-приложение в режим «только чтение».
- **Исключения:** Критические пути, такие как `/accounts/login/`, `/accounts/logout/` и `/core/` (используемый для управления состоянием), освобождены от проверки, чтобы обеспечить базовую работу системы и переходы между состояниями.

## 2. Динамическое обнаружение адресов
Middleware также выполняет пассивное обнаружение точек доступа. Оно отслеживает заголовок `Host` входящих запросов и автоматически регистрирует новые адреса доступа в `GlobalSettings (SETTINGS_ADDRESSES)`. Это гарантирует, что система координации Multi-Master всегда имеет актуальный список адресов для всех экземпляров ARM в кластере.

## 3. Инициализация при запуске (`startup_middleware`)
`startup_middleware` — это «одноразовое» middleware, которое запускается один раз при загрузке системы. Оно:
- Инициализирует состояние Active/Passive системы на основе конфигурации Multi-Master.
- Заполняет `GlobalSettings` значениями по умолчанию, определенными в `core.variables`, гарантируя, что база данных всегда находится в согласованном и функциональном состоянии.

# Система распределенного кэширования

Система PUM использует высокоразвитый слой кэширования, построенный на базе Redis, предоставляющий нечто большее, чем простое хранилище «ключ-значение».

## 1. Расширенные декораторы кэширования (`core/cache/utils.py`)

### 1.1. `@periodic_cache`
Этот декоратор предназначен для данных, получение которых обходится дорого, но которые можно обновлять по расписанию.
- **Фоновое обновление:** Вместо обновления по запросу пользователя эти кэши обновляются воркерами Celery (`reload_periodic_cache`).
- **Отслеживание состояния:** В Redis поддерживаются две версии: `CURRENT` и `OLD`. Это позволяет системе выполнять **обнаружение изменений** (Change Detection), подробнее см. в [анализе Redis](##redis).
- **Хуки на обновление:** Разработчики могут предоставить обратный вызов `on_update` (с функциями `filter` and `result`), который срабатывает только тогда, когда кэшированные данные действительно изменяются.

### 1.2. `@redis_cached`
Более традиционный кэш с истекающим сроком действия и несколькими расширенными функциями:
- **Поддержка асинхронности:** Нативная поддержка декорирования функций `async def`.
- **Принудительная перезагрузка:** Поддерживает параметр `reload=True` для обхода кэша и получения свежих данных.
- **Автоматическая инвалидация:** Предоставляет метод `.clear_cache()` для декорированной функции для ручной инвалидации.

## 2. Распределенный жизненный цикл

1. **Регистрация:** Когда функция декорируется, она автоматически регистрируется в списке `REDIS_PERIODIC_CACHE` в Redis.
2. **Выполнение:** Декоратор сначала проверяет Redis на наличие валидного, не просроченного результата.
3. **Синхронизация:** Для `periodic_cache` воркер Celery перебирает зарегистрированные функции, вызывает их, сравнивает результат с версией `OLD` и при необходимости запускает хуки обновления.

Такая архитектура гарантирует, что веб-интерфейс остается чрезвычайно отзывчивым, обслуживая данные из Redis, в то время как тяжелая работа (например, опрос более 100 аппаратных устройств) полностью выполняется в фоновом режиме.

# Движок синхронизации данных

Модуль `core/cache/sync.py` реализует надежный движок для синхронизации внутренних моделей Django с внешними источниками данных (такими как GLPI или специализированные контроллеры оборудования).

## 1. Сопоставление объектов и обнаружение переименований

Одной из самых сложных проблем в распределенных системах является отслеживание объектов, которые могут быть переименованы во внешнем источнике. Движок синхронизации решает эту проблему с помощью стратегии «двойной проверки»:

1. **Проверка по индексу:** Сначала он пытается найти объект, используя его основной идентификатор (например, `name` или `serial_number`), в Redis Hash (`RedisHashTable`).
2. **Проверка по внешнему ID:** Если объект не найден по имени, он ищет в Redis Hash `foreignid` объекта (ID во внешней системе).
3. **Обработка переименования:** Если объект найден по `foreignid`, система понимает, что он был переименован. Она обновляет внутренние сопоставления в Redis и переименовывает экземпляр модели Django в соответствии с новым внешним именем.
4. **Создание:** Если ни одна из проверок не увенчалась успехом, создается новый экземпляр модели Django.

## 2. Протокол `model.sync()`

Модели, участвующие в синхронизации, должны реализовать метод-генератор `sync(data)`.
- **Обязанность:** Метод `sync` модели отвечает за сопоставление внешнего словаря `data` со своими полями.
- **Паттерн генератора:** Он использует `yield self`, чтобы обеспечить гибкую логику сохранения и возможные побочные эффекты (например, создание связанных объектов) в процессе синхронизации.

## 3. Транзакционная безопасность

Движок синхронизации использует задачу Celery `reload_periodic_sync` для организации процесса. Он собирает все объекты, подлежащие сохранению, и выполняет обновления базы данных с помощью `database_sync_to_async(s.save)()`, гарантируя, что база данных остается источником истины, используя при этом скорость Redis для поиска объектов и отслеживания переименований.

# Middleware динамического JSON API

Система PUM включает в себя высокотехнологичное `json_middleware`, которое позволяет всему приложению выступать одновременно как традиционное многостраничное веб-приложение, так и как REST-подобный JSON API без необходимости дублирования логики представлений.

## 1. Автоматическая генерация API

Middleware (в `products_app/middleware/json.py`) динамически преобразует представления, рендерищие шаблоны, в представления, возвращающие JSON.

- **Триггер:** Любой запрос с параметром запроса `?json=true` будет обрабатываться движком JSON.
- **Monkey-patching (динамическое исправление):** При первом таком запросе middleware сканирует все зарегистрированные представления в проекте и исправляет их методы `get` и `post`, а также стандартную функцию Django `loader.render_to_string`.

## 2. Перехват контекста и сериализация

Когда представление вызывается с `json=true`:
1. **Захват контекста:** Middleware перехватывает словарь Context, который представление обычно передает в свой HTML-шаблон.
2. **Извлечение ошибок формы:** Если представление содержит форму Django (например, форму входа или конфигурации), middleware автоматически извлекает любые ошибки валидации.
3. **Рекурсивная сериализация:** Оно передает контекст и ошибки движку `jsonify`, преобразуя сложные объекты базы данных, наборы запросов (QuerySets) и временные метки в чистую структуру JSON.
4. **Отображение редиректов:** Перенаправления HTTP (301/302) преобразуются в JSON-ответ: `{"url_redirect": "/new/path/"}`.

## 3. Фильтрация на стороне клиента

Уникальной особенностью этого middleware является возможность клиента запрашивать только определенные части контекста для экономии трафика.

- **Использование:** Добавляя параметры `json_<key>` в URL, клиент может фильтровать вывод.
- **Пример:** `GET /products/1/?json=true&json_name&json_state`
  - Middleware перехватит полный контекст продукта, но вернет только поля `name` и `state` в итоговом JSON-ответе.

## 4. Интеграция со слоем производительности

- **Кэширование:** Middleware учитывает декоратор `json_cached`. Если у представления есть предварительно вычисленная JSON-версия в Redis, middleware отдаст ее напрямую, полностью минуя выполнение представления.
- **Поддержка асинхронности:** Middleware полностью совместимо с асинхронными представлениями Django, предоставляя обертку `async_newf`, которая корректно обрабатывает вызовы `await` во время генерации контекста.

## 5. Преимущества для разработчика

Эта архитектура позволяет разработчикам писать стандартные представления Django на основе классов (CBV), сосредоточенные на данных и бизнес-логике. `json_middleware` берет на себя сложность автоматического предоставления этой же логики мобильным приложениям, внешним скриптам или современным фронтенд-фреймворкам.
